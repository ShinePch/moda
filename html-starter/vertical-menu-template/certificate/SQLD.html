모델링

1-1. 모델링의 특징
분류 암기 정의 EVC 시스템 예시 설명
단순 단 물리적으로 존재하는 객체 evc_member (회원), evc_member_card (충전카드) "손으로 만질 수 있는 실체가 있는 녀석들!"
추상 추 논리적으로 존재하는 개념 evc_member_group (회원그룹) "머릿속 개념이지만 관리가 필요한 놈들!"
명확 명 시간에 따라 발생하는 이벤트 charging_transaction, charging_payment "뭔가 일어났을 때만 생기는 기록들!"
1-2. 모델링의 유의사항
분류 암기 정의 EVC 시스템 예시 특징
유연성 유 독립적으로 생성 가능 evc_member, evc_member_group "혼자서도 당당하게 살 수 있는 독립적인 놈!"
유일성 유 기본 엔터티 간 관계 표현 evc_member_card "둘 사이를 이어주는 다리 역할!"
명확성 명 행위나 이벤트 저장 charging_transaction, charging_payment "뭔가 액션이 일어나면 기록하는 일기장!"
1-3. 모델링의 관점
분류 암기 정의 EVC 시스템 예시 특징
Creat C 독립적으로 생성 가능 evc_member, evc_member_group "혼자서도 당당하게 살 수 있는 독립적인 놈!"
Read R 기본 엔터티 간 관계 표현 evc_member_card "둘 사이를 이어주는 다리 역할!"
Upadate U 행위나 이벤트 저장 charging_transaction, charging_payment "뭔가 액션이 일어나면 기록하는 일기장!"
Delete D 행위나 이벤트 저장 charging_transaction, charging_payment "뭔가 액션이 일어나면 기록하는 일기장!"
1-4. 모델링의 단계
분류 암기 정의 EVC 시스템 예시 특징
개념적 모델링 개 독립적으로 생성 가능 evc_member, evc_member_group "혼자서도 당당하게 살 수 있는 독립적인 놈!"
논리적 모델링 논 기본 엔터티 간 관계 표현 evc_member_card "둘 사이를 이어주는 다리 역할!"
물리적 모델링 물 행위나 이벤트 저장 charging_transaction, charging_payment "뭔가 액션이 일어나면 기록하는 일기장!"
1-5. 모델 트렌젝션
분류 암기 정의
원자성(Atomicity) 원 모두 수정되거나 말거나
일관성(consistency) 일 전 후로 일관
고립성(Isolation) 고 노 관섭
지속성(Durability) 지 영구적 저장
🏷️ 엔터티 & 속성

1-1. 유형과 무형에 따른 엔터티 종류
분류 암기 정의 EVC 시스템 예시 설명
개념 엔터티 개 논리적으로 존재하는 개념 evc_member_group (회원그룹) "머릿속 개념이지만 관리가 필요한 놈들!"
사건 엔터티 사 시간에 따라 발생하는 이벤트 charging_transaction, charging_payment "뭔가 일어났을 때만 생기는 기록들!"
유형 엔터티 유 물리적으로 존재하는 객체 evc_member (회원), evc_member_card (충전카드) "손으로 만질 수 있는 실체가 있는 녀석들!"
1-2. 발생 시점에 따른 엔터티 종류
분류 암기 정의 EVC 시스템 예시 특징
기본 엔터티 기 독립적으로 생성 가능 evc_member, evc_member_group "혼자서도 당당하게 살 수 있는 독립적인 놈!"
중심 엔터티 중 기본 엔터티 간 관계 표현 evc_member_card "둘 사이를 이어주는 다리 역할!"
행위 엔터티 행 행위나 이벤트 저장 charging_transaction, charging_payment "뭔가 액션이 일어나면 기록하는 일기장!"

2-1. 특성에 따른 속성 종류
분류 암기 정의 EVC 예시 설명
기본 속성 기 업무로부터 추출한 속성 member_name, mobile, email "현실에서 바로 가져온 날것 그대로!"
설계 속성 설 설계 과정에서 도출된 속성 member_id, charging_transaction_id "개발자가 편의를 위해 만든 인공적인 놈!"
파생 속성 파 다른 속성으로부터 계산되는 속성 charging_fee (charging_kwh × transaction_cost) "다른 놈들을 조합해서 계산으로 만든 놈!"
2-2. 분해 여부에 따른 속성 종류
분류 암기 정의 EVC 예시 설명
다중값 속성 다 여러 개의 값을 가질 수 있는 속성 email_yn + sms_yn (여러 수신동의 설정) "하나가 아니라 여러 개 값을 담을 수 있어!"
단일 속성 단 더 이상 분해되지 않는 속성 member_name (회원명), mobile (핸드폰번호) "더 쪼갤 수 없는 최소 단위!"
복합 속성 복 여러 개의 의미 있는 단위로 분해 가능 addr + addr_detail (주소 = 기본주소+상세주소) "큰 덩어리를 의미별로 나눌 수 있는 놈!"
2-3. 구성 방식에 여부에 따른 분류
분류 정의 EVC 예시 설명
기본키 여러 개의 값을 가질 수 있는 속성 email_yn + sms_yn (여러 수신동의 설정) "하나가 아니라 여러 개 값을 담을 수 있어!"
외래키 더 이상 분해되지 않는 속성 member_name (회원명), mobile (핸드폰번호) "더 쪼갤 수 없는 최소 단위!"
일반속성 여러 개의 의미 있는 단위로 분해 가능 addr + addr_detail (주소 = 기본주소+상세주소) "큰 덩어리를 의미별로 나눌 수 있는 놈!"
🔑 식별자 & 관계

3-1. 대표성 여부에 따른 식별자 종류
분류 정의 EVC 예시 설명
주식별자 엔터티 대표 식별자 member_id (PK), charging_transaction_id (PK) "이 테이블의 대장! 얘로 모든 걸 구분해!"
보조식별자 참조나 조회용 식별자 mobile, email (유니크하지만 PK 아님) "대장은 아니지만 구분은 가능한 부대장!"
3-2. 생성 여부에 따른 식별자 종류
분류 정의 EVC 예시 설명
내부 식별자 엔터티 내부에서 스스로 생성 member_id, payment_id "내 안에서 자체 생산한 고유번호!"
외부 식별자 다른 엔터티로부터 받아온 식별자 member_card의 member_id (FK) "다른 테이블에서 빌려온 참조키!"
3-3. 속성 수에 따른 식별자 종류
분류 정의 EVC 예시 설명
단일 식별자 하나의 속성으로 구성 member_id, payment_id "하나만으로도 충분한 심플한 놈!"
복합 식별자 여러 속성의 조합으로 구성 evc_member_card의 (member_card_seq + member_card_no + member_id) "여러 개를 합쳐야 유일해지는 팀플레이어!"
3-4. 대체 여부에 따른 식별자 종류
분류 정의 EVC 예시 설명
본질 식별자 업무적 의미를 가진 식별자 member_card_no (실제 카드번호) "현실에서 정말 의미있는 진짜 식별자!"
인조 식별자 시스템에서 인위적으로 생성 member_id, charging_transaction_id "편의를 위해 개발자가 만든 가짜(?) 식별자!"

4-1. 관계의 종류
분류 정의 EVC 예시 설명
존재 관계 존재에 의한 관계 회원 - 회원카드 (회원이 있어야 카드가 존재) "부모 없이는 자식도 없어!"
행위 관계 행위에 의한 관계(행위,동작,사건) 회원카드 - 충전내역 (카드로 충전행위 발생) "뭔가 액션이 일어나면서 생기는 관계!"
4-2. 관계 차수
차수 정의 EVC 예시 설명
1:1 일대일 관계 회원 : 회원그룹 (한 회원은 한 그룹에만) "나는 너만 봐, 너도 나만 봐!"
1:N 일대다 관계 회원 : 충전내역 (한 회원이 여러 번 충전) "나는 하나, 너희는 여럿!"
M:N 다대다 관계 회원 : 카드 (한 회원이 여러 카드, 한 카드를 여러 회원 공유 가능) "우리 모두 자유롭게 연결돼!"
4-3. 관계 구성
차수 암기 정의 EVC 예시 설명
관계명 관 일대일 관계 회원 : 회원그룹 (한 회원은 한 그룹에만) "나는 너만 봐, 너도 나만 봐!"
차수(Cadinality) 차 일대다 관계 회원 : 충전내역 (한 회원이 여러 번 충전) "나는 하나, 너희는 여럿!"
선택사항 선 다대다 관계 회원 : 카드 (한 회원이 여러 카드, 한 카드를 여러 회원 공유 가능) "우리 모두 자유롭게 연결돼!"

특성 정의 EVC 예시 설명
유일성 각 인스턴스를 유일하게 구분 member_id는 모든 회원마다 다름 "절대 겹치면 안 되는 고유함!"
최소성 꼭 필요한 최소한의 속성만 사용 PK는 꼭 필요한 것만 포함 "군더더기 없이 딱 필요한 것만!"
불변성 한 번 정해지면 변하지 않음 member_id는 계속 동일 "한번 정하면 평생 그대로!"
존재성 반드시 값이 존재해야 함 PK는 NULL 불가 "빈 값은 절대 안돼!"
대표성 해당 엔터티를 대표할 수 있음 member_id로 회원 전체를 대표 "이 테이블하면 바로 생각나는 대표주자!"
특성 정의 설명
식별자 생명주기, Not Null, 필수 "절대 겹치면 안 되는 고유함!"
비식별자 다른 생명주기, Null 허용, 선택, 일반속성 "군더더기 없이 딱 필요한 것만!"
특성 정의 EVC 예시 설명
후보키 학번, 주민번호 member_id는 모든 회원마다 다름 "유일성, 최소성 만족!"
기본키 학번 PK는 꼭 필요한 것만 포함 "후보키중 대표성, 개체 무결성!"
대체키 주민번호 member_id는 계속 동일 "기본키를 제외한 키!"
슈퍼키 학번+주민번호 but 굳이? PK는 NULL 불가 "유일성은 만족 최소성은 불만족!"
외래키 다른 키를 참조 member_id로 회원 전체를 대표 "참조 무결성!"
특성 정의
개체무결성 Not Null
참조무결성 참조 없는 외래키는 없음
📐 정규화 & 최적화

💡 정규화란?

데이터의 중복을 제거하고 데이터 무결성을 유지하기 위해 테이블을 분할하는 과정이야! "깔끔하게 정리정돈 하는 것!"

1-1. 이상현상
분류 정의
삽입이상 의도치 않은 삽입
삭제이상 의도치 않은 삭제
갱신이상 의도치 않은 갱신
1-2. 정규화
함수적 종속 (A 속성에 의해 B가 유일하게 결정 A > B)
A: 결정자 B: 종속자
단계 목적 EVC 적용 예시 해결되는 문제
1NF
(제1정규형)		 반복 그룹 제거 * 회원 테이블에서 여러 전화번호를 별도 테이블로 분리
* 종속자가 기본키의 모든 속성에 종속적인 경우		 "한 칸에 여러 값 넣지 마!"
2NF
(제2정규형)		 부분 함수 종속 제거 * 복합키에서 일부분에만 종속된 속성 분리
* 종속자가 기본키의 일부 속성에 종속적인 경우		 "반쪽짜리 의존은 안 돼!"
3NF
(제3정규형)		 이행 함수 종속 제거 회원 → 그룹 → 그룹명 (직접 참조로 변경) "우회해서 의존하지 마!"
BCNF
(보이스-코드정규형)		 결정자가 후보키가 아닌 함수 종속 제거 교수 - 과목 - 학생 관계에서 교수가 여러 과목 담당시 분리 "권한 없는 놈이 결정하지 마!"
✅ 정규화의 장점
  • 데이터 중복 최소화
  • 데이터 무결성 향상
  • 저장 공간 절약
  • 데이터 일관성 유지
⚠️ 정규화의 단점
  • JOIN 연산 증가
  • 조회 성능 저하 가능
  • 복잡한 쿼리 필요
  • 테이블 수 증가

🔄 반정규화 (Denormalization)
반정규화란? 성능 향상을 위해 의도적으로 중복을 허용하는 것!
"때로는 깔끔함보다 속도가 중요해!"
반정규화 기법 설명 예시
테이블 통합 자주 조인되는 테이블을 하나로 합침 회원 + 회원상세정보 → 회원통합테이블
컬럼 중복 자주 참조되는 컬럼을 여러 테이블에 중복 저장 주문테이블에 고객명 컬럼 추가
계산 컬럼 추가 계산 결과를 미리 저장 총주문금액, 평균평점 등을 별도 저장
🔍 인덱스 최적화
인덱스 종류 용도 언제 사용? 주의사항
B-Tree 인덱스 일반적인 검색 최적화 범위 검색, 정렬이 필요할 때 "만능이지만 완벽하지는 않아!"
비트맵 인덱스 카디널리티가 낮은 컬럼 성별, 등급 같은 값이 적을 때 "종류가 적을 때만 효과적!"
복합 인덱스 여러 컬럼 동시 검색 WHERE 조건에 여러 컬럼 사용시 "순서가 중요해!"

1. 집계 함수
함수명 용도 설명 예시
COUNT 갯수 세기 "야, 이 테이블에 몇 개 행이 있는지 세어봐!" COUNT(*), COUNT(column_name)
SUM 합계 구하기 "모든 숫자를 다 더해줘!" SUM(charging_fee)
AVG 평균 구하기 "전체의 평균이 얼마인지 알려줘!" AVG(charging_kwh)
MAX 최댓값 찾기 "제일 큰 놈이 누구야?" MAX(payment_amount)
MIN 최솟값 찾기 "제일 작은 놈이 누구야?" MIN(payment_amount)
💻 집계 함수 실전 예시
mariaDB DBeaver 안먹힘mariaDB DBeaver 안먹힘 
          -- 직원 테이블 기본 통계 한눈에 보기
SELECT 
    COUNT(*) as 총직원수,           -- "야, 직원이 몇 명이야?"
    SUM(salary) as 총급여합계,      -- "전체 급여 다 더하면 얼마야?"
    AVG(salary) as 평균급여,       -- "평균 급여는 얼마야?"
    MAX(salary) as 최고급여,       -- "제일 많이 받는 사람 급여는?"
    MIN(salary) as 최저급여        -- "제일 적게 받는 사람 급여는?"
FROM employees;

-- 부서별 집계 함수 활용
SELECT 
    d.dept_name as 부서명,
    COUNT(*) as 직원수,
    SUM(e.salary) as 부서급여총합,
    AVG(e.salary) as 부서평균급여,
    MAX(e.salary) as 부서최고급여,
    MIN(e.salary) as 부서최저급여
FROM employees e
JOIN departments d ON e.dept_id = d.dept_id
GROUP BY d.dept_name
ORDER BY 부서평균급여 DESC;
2. 그룹 함수
함수명 용도 특징 설명
ROLLUP 소그룹 간의 소계 및 총계 부분적 계산 "단계별로 소계를 만들어줘! (계층적)"
CUBE 다차원적 소계 및 총계 총 계산 "모든 조합의 소계를 다 만들어줘! (전방위)"
GROUPING 소계행 구분 NULL 대신 원하는 텍스트 표시 "소계행인지 일반행인지 구분해줘!"
GROUPING SETS 특정 소계 계산 원하는 조합만 선택적 계산 "내가 원하는 소계만 골라서 만들어줘!"
💻 그룹 함수 실전 예시
mariaDB DBeaver 안먹힘mariaDB DBeaver 안먹힘 
          -- ROLLUP: 부서별, 직급별 급여 소계를 계층적으로!
SELECT 
    d.dept_name as 부서, 
    p.pos_name as 직급, 
    SUM(e.salary) as 급여합계
FROM employees e
JOIN departments d ON e.dept_id = d.dept_id
JOIN positions p ON e.pos_id = p.pos_id
GROUP BY ROLLUP(d.dept_name, p.pos_name)
ORDER BY d.dept_name, p.pos_name;
-- 결과: 각 부서의 직급별 소계 + 부서별 총계 + 전체 총계

-- CUBE: 모든 가능한 조합으로 소계를 내줘 (더 자세한 분석)
SELECT 
    d.dept_name as 부서, 
    p.pos_name as 직급, 
    SUM(e.salary) as 급여합계
FROM employees e
JOIN departments d ON e.dept_id = d.dept_id
JOIN positions p ON e.pos_id = p.pos_id
GROUP BY CUBE(d.dept_name, p.pos_name)
ORDER BY d.dept_name, p.pos_name;
-- 결과: 부서별, 직급별, 부서+직급별, 전체 - 모든 조합!

-- GROUPING: NULL 대신 예쁜 텍스트로 보여줘!
SELECT 
    CASE WHEN GROUPING(d.dept_name) = 1 THEN '전체부서' ELSE d.dept_name END as 부서,
    CASE WHEN GROUPING(p.pos_name) = 1 THEN '전체직급' ELSE p.pos_name END as 직급,
    SUM(e.salary) as 급여합계
FROM employees e
JOIN departments d ON e.dept_id = d.dept_id
JOIN positions p ON e.pos_id = p.pos_id
GROUP BY ROLLUP(d.dept_name, p.pos_name)
ORDER BY d.dept_name, p.pos_name;

-- GROUPING SETS: 부서별 합계와 직급별 합계만 따로 보고 싶어!
SELECT 
    d.dept_name as 부서, 
    p.pos_name as 직급, 
    SUM(e.salary) as 급여합계
FROM employees e
JOIN departments d ON e.dept_id = d.dept_id
JOIN positions p ON e.pos_id = p.pos_id
GROUP BY GROUPING SETS((d.dept_name), (p.pos_name), ())
ORDER BY d.dept_name, p.pos_name;
3. 윈도우 함수 - 집계 함수
함수명 용도 설명
COUNT() OVER() 윈도우 내 갯수 "파티션별로 갯수 세어줘!"
SUM() OVER() 윈도우 내 합계 "파티션별로 누적 합계 만들어줘!"
AVG() OVER() 윈도우 내 평균 "파티션별로 이동 평균 구해줘!"
💻 윈도우 집계 함수 실전 예시
mariaDB DBeaver 안먹힘mariaDB DBeaver 안먹힘 
          -- 각 직원의 급여와 함께 부서별 통계도 보임!
SELECT 
    e.name as 이름,
    d.dept_name as 부서,
    p.pos_name as 직급,
    e.salary as 개인급여,
    AVG(e.salary) OVER(PARTITION BY d.dept_name) as 부서평균급여,
    COUNT(*) OVER(PARTITION BY d.dept_name) as 부서인원수,
    SUM(e.salary) OVER(PARTITION BY d.dept_name) as 부서급여총합,
    SUM(e.salary) OVER() as 전체급여총합
FROM employees e
JOIN departments d ON e.dept_id = d.dept_id
JOIN positions p ON e.pos_id = p.pos_id
ORDER BY d.dept_name, e.salary DESC;
-- 각 행마다 자기 부서의 통계가 함께 나와!
4. 윈도우 함수 - 순위 함수
함수명 순위 매기는 방식 동점자 처리 예시 결과 설명
RANK 일반적인 순위 같은 순위면 존재하는 수만큼 건너뜀 1, 2, 3, 3, 5... "공동 3등이 2명이면 다음은 5등!"
DENSE_RANK 밀집된 순위 같은 순위더라도 건너뛰지 않음 1, 2, 3, 3, 4, 5... "공동 3등이 있어도 다음은 4등!"
ROW_NUMBER 강제 고유 순위 동일한 값이라도 각기 다른 순위 1, 2, 3, 4, 5... "무조건 다른 번호를 줘!"
💻 순위 함수 실전 예시
mariaDB DBeaver 안먹힘mariaDB DBeaver 안먹힘 
          -- 급여 순위를 3가지 방법으로 매김!
SELECT 
    e.name as 이름,
    d.dept_name as 부서,
    p.pos_name as 직급,
    e.salary as 급여,
    RANK() OVER(ORDER BY e.salary DESC) as 전체순위_건너뜀,        -- 1,2,3,3,5,6
    DENSE_RANK() OVER(ORDER BY e.salary DESC) as 전체순위_연속,    -- 1,2,3,3,4,5  
    ROW_NUMBER() OVER(ORDER BY e.salary DESC) as 행번호           -- 1,2,3,4,5,6
FROM employees e
JOIN departments d ON e.dept_id = d.dept_id
JOIN positions p ON e.pos_id = p.pos_id
ORDER BY e.salary DESC;

-- 부서별로 급여 순위 매기기
SELECT 
    e.name as 이름,
    d.dept_name as 부서,
    p.pos_name as 직급,
    e.salary as 급여,
    RANK() OVER(PARTITION BY d.dept_name ORDER BY e.salary DESC) as 부서내순위,
    DENSE_RANK() OVER(PARTITION BY d.dept_name ORDER BY e.salary DESC) as 부서내밀집순위
FROM employees e
JOIN departments d ON e.dept_id = d.dept_id
JOIN positions p ON e.pos_id = p.pos_id
ORDER BY d.dept_name, e.salary DESC;
5. 윈도우 함수 - 행순서 함수
함수명 용도 참조 방향 설명
FIRST_VALUE 파티션별 첫 번째 데이터 맨 앞 "이 그룹에서 제일 앞에 있는 놈 데려와!"
LAST_VALUE 파티션별 마지막 데이터 맨 뒤 "이 그룹에서 제일 뒤에 있는 놈 데려와!"
LAG 특정 수만큼 앞선 데이터 이전 "n번째 앞에 있던 놈의 값 가져와!"
LEAD 특정 수만큼 뒤의 데이터 이후 "n번째 뒤에 있을 놈의 값 가져와!"
💻 행순서 함수 실전 예시
mariaDB DBeaver 안먹힘mariaDB DBeaver 안먹힘 
          -- 부서별 1등, 꼴등 그리고 앞뒤 사람 급여 비교!
SELECT 
    e.name as 이름,
    d.dept_name as 부서,
    p.pos_name as 직급,
    e.salary as 급여,
    FIRST_VALUE(e.name) OVER(PARTITION BY d.dept_name ORDER BY e.salary DESC) as 부서최고급여자,
    LAST_VALUE(e.name) OVER(PARTITION BY d.dept_name ORDER BY e.salary DESC 
                          ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING) as 부서최저급여자,
    LAG(e.salary, 1) OVER(PARTITION BY d.dept_name ORDER BY e.salary DESC) as 바로앞사람급여,
    LEAD(e.salary, 1) OVER(PARTITION BY d.dept_name ORDER BY e.salary DESC) as 바로뒤사람급여
FROM employees e
JOIN departments d ON e.dept_id = d.dept_id
JOIN positions p ON e.pos_id = p.pos_id
ORDER BY d.dept_name, e.salary DESC;

-- 월별 매출 증감률 구하기 (매출 테이블 활용)
SELECT 
    d.dept_name as 부서명,
    DATE_FORMAT(s.sale_month, '%Y-%m') as 월,
    s.amount as 당월매출,
    LAG(s.amount, 1) OVER(PARTITION BY d.dept_name ORDER BY s.sale_month) as 전월매출,
    s.amount - LAG(s.amount, 1) OVER(PARTITION BY d.dept_name ORDER BY s.sale_month) as 증감액,
    ROUND((s.amount - LAG(s.amount, 1) OVER(PARTITION BY d.dept_name ORDER BY s.sale_month)) 
          / LAG(s.amount, 1) OVER(PARTITION BY d.dept_name ORDER BY s.sale_month) * 100, 2) as 증감률
FROM sales s
JOIN departments d ON s.dept_id = d.dept_id
WHERE s.amount > 0  -- 수익 부서만
ORDER BY d.dept_name, s.sale_month;
6. 윈도우 함수 - 비율 함수
함수명 용도 결과 범위 설명
RATIO_TO_REPORT 파티션별 합계 대비 비율 0 ~ 1 "전체에서 내가 차지하는 비율이 얼마야?"
PERCENT_RANK 백분위 순위 0 ~ 1 (맨 위=0, 맨 아래=1) "내가 상위 몇 %에 있는지 알려줘!"
CUME_DIST 누적 백분율 0보다 크고 1보다 작은 값 "나보다 작거나 같은 놈이 전체의 몇 %야?"
NTILE n등분 후 등급 부여 1 ~ n "전체를 n등분해서 몇 등급에 속하는지 알려줘!"
💻 비율 함수 실전 예시
mariaDB DBeaver 안먹힘mariaDB DBeaver 안먹힘 
          -- 급여 비율과 순위를 다각도로 분석!
SELECT 
    e.name as 이름,
    d.dept_name as 부서,
    p.pos_name as 직급,
    e.salary as 급여,
    ROUND(RATIO_TO_REPORT(e.salary) OVER() * 100, 2) as 전체급여대비비율,
    ROUND(PERCENT_RANK() OVER(ORDER BY e.salary) * 100, 2) as 백분위순위,
    ROUND(CUME_DIST() OVER(ORDER BY e.salary) * 100, 2) as 누적백분율,
    NTILE(4) OVER(ORDER BY e.salary) as 사분위등급  -- 1등급(상위25%), 2등급, 3등급, 4등급(하위25%)
FROM employees e
JOIN departments d ON e.dept_id = d.dept_id
JOIN positions p ON e.pos_id = p.pos_id
ORDER BY e.salary DESC;

-- 부서별 급여 비율 분석
SELECT 
    e.name as 이름,
    d.dept_name as 부서,
    p.pos_name as 직급,
    e.salary as 급여,
    ROUND(RATIO_TO_REPORT(e.salary) OVER(PARTITION BY d.dept_name) * 100, 2) as 부서내급여비율,
    NTILE(3) OVER(PARTITION BY d.dept_name ORDER BY e.salary) as 부서내등급,  -- 상/중/하
    ROUND(PERCENT_RANK() OVER(PARTITION BY d.dept_name ORDER BY e.salary) * 100, 2) as 부서내백분위
FROM employees e
JOIN departments d ON e.dept_id = d.dept_id
JOIN positions p ON e.pos_id = p.pos_id
ORDER BY d.dept_name, e.salary DESC;

-- 부서별 매출 기여도 분석
SELECT 
    d.dept_name as 부서명,
    SUM(s.amount) as 연간매출,
    ROUND(RATIO_TO_REPORT(SUM(s.amount)) OVER() * 100, 2) as 전체매출기여도,
    RANK() OVER(ORDER BY SUM(s.amount) DESC) as 매출순위
FROM sales s
JOIN departments d ON s.dept_id = d.dept_id
WHERE s.amount > 0  -- 수익 부서만
GROUP BY d.dept_name
ORDER BY 연간매출 DESC;
💡 함수 활용 팁
  • 집계 함수: GROUP BY와 함께 사용해서 그룹별 통계!
  • ROLLUP vs CUBE: ROLLUP은 계층적, CUBE는 모든 조합!
  • 윈도우 함수: OVER() 절이 핵심! PARTITION BY로 그룹 나누기!
  • 순위 함수: 동점자 처리 방식이 다르니 상황에 맞게 선택!
  • LAG/LEAD: 시계열 데이터 분석할 때 엄청 유용해!
  • 비율 함수: 상대적 위치나 비율 분석할 때 필수!

1. 테이블 생성 스크립트
            -- ========================================
-- SQL 데이터 분석 함수 실습용 테이블 생성
-- MariaDB 버전
-- ========================================

-- 1. 부서 테이블
CREATE TABLE departments (
    dept_id INT PRIMARY KEY AUTO_INCREMENT,
    dept_name VARCHAR(50) NOT NULL,
    location VARCHAR(50)
);

-- 2. 직급 테이블  
CREATE TABLE positions (
    pos_id INT PRIMARY KEY AUTO_INCREMENT,
    pos_name VARCHAR(30) NOT NULL,
    base_salary INT
);

-- 3. 직원 테이블
CREATE TABLE employees (
    emp_id INT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(50) NOT NULL,
    dept_id INT,
    pos_id INT,
    salary INT,
    hire_date DATE,
    age INT,
    performance_score DECIMAL(3,2), -- 1.00 ~ 5.00 점수
    FOREIGN KEY (dept_id) REFERENCES departments(dept_id),
    FOREIGN KEY (pos_id) REFERENCES positions(pos_id)
);

-- 4. 매출 테이블 (월별 부서 매출)
CREATE TABLE sales (
    sale_id INT PRIMARY KEY AUTO_INCREMENT,
    dept_id INT,
    sale_month DATE,
    amount BIGINT,
    FOREIGN KEY (dept_id) REFERENCES departments(dept_id)
);
💡 테이블 구조
• departments (부서)
• positions (직급)
• employees (직원)
• sales (매출)

5. 확인용 기본 쿼리
            -- 전체 직원 현황 보기
SELECT 
    e.name as 이름,
    d.dept_name as 부서,
    p.pos_name as 직급,
    e.salary as 급여,
    e.age as 나이,
    e.performance_score as 평가점수
FROM employees e
JOIN departments d ON e.dept_id = d.dept_id  
JOIN positions p ON e.pos_id = p.pos_id
ORDER BY d.dept_name, e.salary DESC;

-- 부서별 직원 수와 평균 급여
SELECT 
    d.dept_name as 부서명,
    COUNT(*) as 직원수,
    AVG(e.salary) as 평균급여,
    MAX(e.salary) as 최고급여,
    MIN(e.salary) as 최저급여
FROM employees e
JOIN departments d ON e.dept_id = d.dept_id
GROUP BY d.dept_name
ORDER BY 평균급여 DESC;
